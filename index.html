Goals

Goals and principles

The brief says we are assessed on four things: a reasonably complete application; putting into practice what we covered in lectures and labs; code that is robust and tested before submission, so it does not raise errors or behave strangely; and self-contained code that installs and runs on any machine with core Python. In the grade descriptors attached to the brief, the top bands talk about "major extra features related to the application domain in addition to the required ones", "research has been done", and software "of the quality of commercial applications, competing in terms of features and robustness".

So, in the brief's own terms, our goals are:

  • All 16 required features finished, each one tested by someone other than its author, with no crashes or strange behaviour;
  • On top of that, a few extension features that relate to mental health and have a public basis. Each one counts only if it is finished;
  • Clear code structure that uses what the course taught (functions, classes, file I/O, exception handling, Pandas), with a clear README;
  • Unzip and run with core Python and Tkinter available; initialise the SQLite database automatically; document the one-command launch.

Four principles: ① Keep all features within core Python + Tkinter + sqlite3. ② Network-dependent email needs a clearly labelled offline fallback (not a claim of delivery). ③ Complete and test core requirements before extensions. ④ Reserve substantial time for integration, security and the demonstration.

The brief

The brief at a glance

The NHS has asked us to build TherapyLink: a communication, support and management platform that connects mental health and wellbeing practitioners (MHWPs) with patients. It must be written in core Python, as either a command-line or a GUI application. Ready-made frameworks such as Django, Flask or FastAPI are not allowed. The assessor's machine has only core Python, NumPy and Pandas. All users are already registered, with usernames patient1, mhwp1, … and every password set to the empty string.

Quality requirements

  • Robust GUI: catch errors at callback/service boundaries, show messagebox errors, log details to logs/app.log.
  • Validation: central functions in common/validation.py check names, email, valid calendar dates, appointment slots and predefined conditions; disabled accounts are enforced by services, not just disabled buttons.
  • Persistence: every successful edit commits to SQLite; initialise and seed synthetic test data on first launch; include a documented demo reset.
  • Database safety: parameterised queries, enabled foreign keys, transactions, stable IDs, single MHWP allocation per patient.
  • Environment check: python -m tkinter checks Tk availability; python main.py runs the app; python -m unittest discover -s tests runs tests.
  • README: startup, sample accounts, tests, database location, SMTP setup and offline-notification limitations.

Extension features

The questionnaires, trend alerts and crisis information reflect real practice in mental health services; the README cites the sources. Each person owns one (crisis information and resource recommendations are both small, so P3 gets both); the label shows the owner. None of them is complicated: about 1–3 person-days each.

P6PHQ-9 / GAD-7 questionnaires

What
Patients fill in the depression questionnaire (9 items) and the anxiety questionnaire (7 items) in a Tkinter form. Each item scores 0–3; the total is summed and banded. The MHWP sees each patient's past scores on the dashboard.
How
Questions and bands live in resources/questionnaires.json; scoring is a pure function with unit tests on every band boundary.
Basis
NHS Talking Therapies uses these two questionnaires as standard outcome measures; both are free to use.

P5Mood trend summary and low-mood alert

What
Patient and MHWP both see the 7-day and 30-day average, the longest low-mood streak, and whether the trend is going up or down. After 3 days in a row at level 2 or below, the MHWP sees an alert on login and gets an email.
How
Pandas rolling and resample('W'); the streak is one loop; thresholds live in constants.py.

P3Crisis support information

What
When a mood of 1–2 is logged, or PHQ-9 item 9 is above 0, show NHS 111, Samaritans 116 123 and Shout 85258 straight away, and notify the MHWP.
How
A check at the end of the mood-logging and questionnaire service functions; the text lives in constants.

P4Appointment reminders and rescheduling

What
At login, show appointments in the next 24 hours and the number waiting for confirmation. Patients can reschedule in one step (old one cancelled, new one requested; the email gives both times).

P1Journal search and export

What
Find journal entries by keyword or date range. Moods and journal entries can be exported to CSV (csv module); the MHWP can export a patient report as a text file.

P3Resource recommendations by condition

What
The patient dashboard opens with 3 "exercises for today", matching the patient's conditions and recent mood against resource tags; the more tags match, the higher the item ranks.

P2In-app messages

What
Patients and their MHWP can leave each other messages; the unread count shows on login.

Validation rules

Validation only checks whether what the user typed is correct; it never forces anyone to type something. Optional fields can be skipped with Enter, and typing q at any prompt goes back one level.

GUI behaviour

Tkinter interaction examples

The first document demonstrated full terminal conversations. Their GUI equivalents below describe the screens and the exact behaviour to implement and test.

1 · Login & disabled account

Login window: username and password entries → Authenticate. Redirect by role to Admin, Patient or MHWP dashboard. A disabled user may log in but sees a disabled-account view with only Logout available.

2 · Patient mood entry

Patient dashboard → Mood Tracker → choose coursework colour/level + optional comment → Save. Show success only after database commit; update chart. If one-per-day is adopted, warn before replacing today's record.

3 · Journal

Journal screen → multi-line text input → Save with timestamp → display newest entries first. Only the logged-in patient can view their journal.

4 · Meditation search

Search field + results ttk.Treeview. Filter a curated resource list by keyword; Open Resource launches a source URL through webbrowser.

5 · Appointment calendar

Patient sees the allocated practitioner's weekly grid. Click available time → Request → status REQUESTED. MHWP sees requested bookings and can Confirm or Cancel; conflicting times cannot be reserved.

6 · Notifications

After confirm/cancel, send via SMTP and display accurate result. Offline fallback is a labelled unsent outbox item, never “email delivered”.

7 · MHWP patient record

Assigned-patient table → select patient → predefined condition list and notes form. Author/date recorded; other practitioners cannot access this patient.

8 · MHWP dashboard & charts

Summary cards: assigned patients, latest moods, upcoming appointments. Use tkinter.Canvas to draw mood history from SQLite query results.

9 · Admin management

Admin ttk.Notebook: users, allocations, weekly booking summary. Confirm deletion; allow disable without preventing login; ensure one MHWP per patient.

Starter implementation

Minimal code skeleton — no framework

These snippets illustrate the shared architecture; they are a starting contract, not a finished application.

1 · Database initialisation (Person 1)

import sqlite3
from pathlib import Path

DB_PATH = Path(__file__).resolve().parents[2] / "therapylink.db"

def connect():
    con = sqlite3.connect(DB_PATH)
    con.row_factory = sqlite3.Row
    con.execute("PRAGMA foreign_keys = ON")
    return con

def initialise():
    with connect() as con:
        con.execute("""CREATE TABLE IF NOT EXISTS users (
            id INTEGER PRIMARY KEY,
            username TEXT NOT NULL UNIQUE,
            password TEXT NOT NULL DEFAULT '',
            role TEXT NOT NULL CHECK(role IN ('admin','patient','mhwp')),
            disabled INTEGER NOT NULL DEFAULT 0 CHECK(disabled IN (0,1))
        )""")

# service layer (called by a Tkinter button callback)
def get_patient_moods(connection, patient_id):
    return connection.execute(

Process

How we work

Git

  • main only changes through PRs, reviewed by your backup partner
  • Branches like feature/p4-booking; push at least once a day
  • Every PR says what it does and how it was tested
  • data/, config.json and logs/ are in .gitignore

Definition of done

  • The feature works end to end from the menu
  • Bad input gets a message; disabled users are refused
  • At least one unit test; python -m unittest passes
  • Its acceptance checklist line was ticked by someone else
  • Functions have docstrings; no leftover debug prints

Testing

  • Unit tests: validators, appointment state changes, questionnaire scoring, trend statistics
  • Service tests: with data files in a temporary folder, run through booking, disabling and deleting
  • Acceptance checklist: ticked by hand, role by role, on a different machine
